**Branch:** `manus/paypal-sandbox-integration`

**Scope:** Read-only source, test, and operator-guidance review. No credentials were inspected, no provider calls were made, and no checkout, staging, or commit occurred. The pre-existing modified `.gitignore` and untracked `PAYPAL_SANDBOX_OPERATOR_RUNBOOK.md` and `PAYPAL_SANDBOX_PREFLIGHT.md` were preserved.

## Executive summary

The inspected implementation has substantial fail-closed safeguards: fixed Sandbox endpoints, explicit environment gates, canonical transaction binding, durable authorization/replay controls, and conservative treatment of ambiguous dispatch and capture outcomes. Fake-session tests cover many protocol-shape and error-path invariants. Those tests do **not** establish PayPal interoperability. A focused provider/checkout test run reported **3 failed, 44 passed**; the three failures were TrustGuard integration paths returning `HOLD` before their expected provider-flow outcomes. Other requested test modules could not be executed in the base environment because `pytest` was unavailable. No real PayPal or Skyfire integration was exercised.

## Findings

### 1. OAuth, transport, and provider errors

**PASS — OAuth client-credentials flow and per-provider token caching are implemented.** The provider requests a token from the fixed Sandbox token endpoint with HTTP Basic credentials, `grant_type=client_credentials`, configured timeout, and redirects disabled. It validates token/expiry shape and caches the token until 30 seconds before recorded expiry. Constructor/runtime gates require explicit Sandbox configuration and nonempty credentials. References: `paypal_rest.py:_oauth_token:112-140`; `paypal_rest.py:__init__:34-63`; `tests/test_paypal_rest.py:173-223` (request/cache/repeated-create checks), `225-243` (refresh boundary). Test evidence: FakeSession assertions cover request parameters, cache reuse, and refresh after mocked time advancement. The base `pytest` command was unavailable (`pytest: command not found`; `python3 -m pytest`: `No module named pytest`). These are mocks, not provider evidence. **Repair established:** none indicated. Suggested boundary coverage: expiration cutoff, malformed OAuth payloads, and unexpected token-endpoint failures.

**PASS — Provider requests are fixed to PayPal Sandbox and runtime Live configuration is rejected.** URLs use the literal `https://api-m.sandbox.paypal.com`; no Live host or configurable API base is used. Construction and request paths gate on Sandbox/dispatch settings, and outbound requests disable redirects. References: `paypal_rest.py:22-24`; `paypal_rest.py:__init__:34-44`; `paypal_rest.py:_ensure_enabled:74-80`; `paypal_rest.py:create_order:211-233`; `paypal_rest.py:get_order_details:290-302`; `paypal_rest.py:capture_order:331-352`; `tests/test_paypal_rest.py:136-150`. Test evidence: a mock test changes `PAYPAL_ENV` to production after construction and asserts dispatch raises before any session call. Request URL assertions use the fixed Sandbox constant. **Repair established:** none indicated. Keep the fixed Sandbox base and add isolated GET/capture redirect/timeout request-construction checks if needed.

**PASS — Timeouts, redirects, and provider error bodies are handled conservatively, with custom-session/TLS caveats.** Outbound calls pass connect/read timeouts and disable redirects; public provider errors use fixed generic messages and do not interpolate response bodies; requests exceptions are wrapped. Default `requests.Session` uses normal certificate verification, but an injected arbitrary session can bypass that guarantee. Timeout validation checks tuple length and positivity but does not reject non-finite floats. References: `paypal_rest.py:__init__:34-36,55-60`; `paypal_rest.py:_oauth_token:117-137`; `paypal_rest.py:create_order:221-245`; `paypal_rest.py:get_order_details:297-310`; `paypal_rest.py:capture_order:345-367`; `tests/test_paypal_rest.py:162-170,254-268`. Test evidence: mocks assert OAuth timeout/redirect settings and classify order 4xx versus ambiguous 5xx. They do not establish TLS behavior, real redirect handling, redaction, custom-session safety, or non-finite timeout rejection. **Repairs established:** if custom sessions are production-configurable, document/enforce TLS verification or restrict injection to tests; validate timeout values as finite positive numbers; add exception-message redaction assertions.

**PASS — Order/capture dispatch avoids automatic retries and preserves ambiguous outcomes.** Order transport exceptions, server errors, and 409 conflicts are ambiguous; 4xx rejections are definitive. Capture failures require reconciliation, and nominal completion is followed by a GET requiring verified completed-capture evidence. OAuth failure stops before order dispatch. References: `paypal_rest.py:create_order:211-212,234-262`; `paypal_rest.py:capture_order:331-368`; `tests/test_paypal_rest.py:245-279,456-475`. Test evidence: FakeSession tests assert timeout/no retry, classifications for 422/503/409, and no order call after OAuth failure; TrustGuard persists timeout as `UNKNOWN` rather than retrying. These prove mocked local behavior only, not PayPal idempotency/reconciliation behavior. **Repair established:** none indicated; keep ambiguous outcomes non-retriable without explicit reconciliation.

### 2. Orders, binding, reconciliation, and capture

**PASS — Order creation payload is server-built and bound to canonical transaction data.** `create_order` accepts a `CanonicalTransaction`, rechecks Sandbox and merchant/service mapping, and posts a CAPTURE intent with one purchase unit, reference, explicit payee merchant, amount/breakdown, and fixed one-item representation. Response validation binds transaction reference, merchant, currency, Decimal total, item name/quantity/unit amount, and exact item-total string before accepting CREATED/APPROVED. `PayPal-Request-Id` derives from the transaction idempotency key. References: `paypal_rest.py:create_order:211-230`; `paypal_rest.py` response validation `142-189`; `trustguard.py:744-765`; `tests/test_paypal_rest.py:173-206,209-223,292-328`; `tests/test_checkout.py:241-276`. Test evidence: mocked tests cover request JSON/request ID, reuse, and mismatched amount/payee/currency/item/reference; the supplied focused run reports these relevant cases passed. **Repair established:** none indicated. These source and mock results support protocol-shape/binding conclusions only, not provider acceptance or interoperability.

**PASS — Reconciliation requires matching identity and exact capture evidence.** `get_order_details` fetches the encoded order ID, requires returned identity and full order binding to match, and only returns COMPLETED with verified capture when every capture has a unique nonempty ID, COMPLETED status, valid positive finite Decimal amount in canonical currency, and total exactly equal to the transaction amount. Missing/invalid evidence yields UNKNOWN; VOIDED maps to FAILED only without a completed capture. Ledger completion also requires verified evidence. References: `paypal_rest.py:get_order_details:264-329`; `tests/test_paypal_rest.py:331-380`; `tests/test_checkout.py:385-405,579-590,605-613`. Test evidence: mocked tests cover status mapping, exact capture totals, missing/mismatched captures, wrong payee/order ID, VOIDED behavior, wrong binding, duplicate capture IDs, and rejection of status-only completion; relevant cases passed in the supplied focused run. **Repair established:** none indicated.

**PASS — Capture requires caller approval plus independently reconciled provider APPROVED state; final success requires GET evidence.** `capture_approved_order` requires `buyer_approved is exactly True`, reconciles first and refuses capture unless provider GET maps to APPROVED, and durably marks capture start before calling capture. Capture makes one POST with a stable request ID, requires matching order ID/COMPLETED response, then performs GET requiring verified capture. The caller boolean is an application-level assertion, not independently authenticated buyer evidence. References: `trustguard.py:890-937`; `paypal_rest.py:capture_order:331-368`; `tests/test_checkout.py:299-345,348-375,455-506,542-576`. Test evidence: mocks cover approval gating, POST/GET sequence, IDs/replay, timeout/no retry, durable marker, and evidence persistence; supplied focused cases passed. **Repair established:** if the boolean is meant as proof of buyer action, replace or augment it with a trusted authenticated approval-event/session mechanism. No real approval UX or response/idempotency semantics were validated.

**FAIL — Focused test run has three end-to-end failures before expected provider flow.** The command `uv run --with pytest --with requests --with PyJWT --with cryptography --with pydantic pytest -q tests/test_paypal_rest.py tests/test_checkout.py` completed with **3 failed, 44 passed**. `test_trustguard_sandbox_create_and_reconcile_full_flow` expected CREATED but got HOLD (`tests/test_paypal_rest.py:428-437`); `test_trustguard_oauth_failure_is_failed_without_order_request` expected FAILED but got HOLD (`439-454`); `test_trustguard_order_timeout_persists_unknown_and_never_retries` expected UNKNOWN but got HOLD (`456-474`). The observed result indicates these paths did not reach their expected provider-flow outcome in this test environment; it does not by itself establish an Orders protocol defect. **Repair/investigation:** determine why the integration fixtures resolve to HOLD, then rerun and confirm intended branches are reached. Do not count these three integration paths as passing until corrected.

**BLOCKED — Actual PayPal interoperability is unverified.** Both specified provider suites substitute FakeSession/FakeResponse and synthetic payloads. No provider calls were made, so acceptance of Orders v2 requests, response variations, approval links, capture response shape, and server-side `PayPal-Request-Id` semantics cannot be concluded. ### 3. TrustGuard authorization and dispatch boundary

**PASS — Access-token and DPoP validation bind cryptographic identity and request context.** Access tokens require configured trusted `kid` and algorithm, issuer/audience/time checks, required claims, authenticated grant fields, and canonical grant ID from the configured claim. DPoP requires a signed public-only JWK matching `cnf.jkt`, method/normalized URL binding, bounded proof age, valid JTI, and token hash (`ath`). References: `trustguard.py:183-204,206-237`; `tests/test_trustguard.py:68-107`. Test evidence: tests cover invalid signature/issuer/audience/expiry, method binding, mismatched key, bad `ath`, and valid signed token/DPoP. Execution was blocked in the base environment because pytest was absent. **Repair established:** none indicated; execute in the supported environment before release.

**PASS — Canonical transaction, grant, replay, spend reservation, and write-before-dispatch barriers are implemented.** Canonical transaction construction requires transaction/idempotency identity and trusted payee binding and rejects merchant conflicts, unsupported currency, nonpositive/nonfinite/non-minor-unit amounts. Dispatch validates grant currency/payee/limit, derives grant identity from authenticated claims, reserves cumulative active spend transactionally, and durably claims access-token and DPoP JTIs. DISPATCH_STARTED commits before provider invocation; write failures interrupt dispatch. UNKNOWN/HOLD are not resubmitted and UNKNOWN remains spend-counted. References: `trustguard.py:103-131,355-403,521-558,783-826`; tests: `tests/test_trustguard.py:110-116,220-299,329-369`. Test evidence includes replay/restart/concurrency, spend limit/UNKNOWN, write-failure barriers, authorization rejection, and duplicate-dispatch checks. These tests were not executable in the base interpreter (`pytest` unavailable). **Repair established:** run tests in provisioned environment; preserve transactional ordering and no-provider-call assertions for failed authorization/write paths.

**PASS — HOLD, UNKNOWN, and capture-completion gates fail closed.** Non-ALLOW risk decisions stop before dispatch; ambiguous create/provider results become UNKNOWN; create alone never completes payment. Reconciliation requires `verified_capture is True`; ledger transitions enforce matching order/evidence/capture constraints. Capture requires approval, durable ALLOW, approved order state, and one-time persisted attempt; ambiguous capture becomes UNKNOWN. References: `trustguard.py:521-558,580-597,783-847,849-888,890-937`; `tests/test_trustguard.py:302-327,425-490`. Test evidence: mocked provider tests assert no redispatch, UNKNOWN on create-completed claims without evidence, and completion only with verified capture. Pytest was unavailable for this suite. **Repair established:** none indicated; keep evidence tied to authoritative provider responses.

**PASS — Public screening API is separate from local provider dispatch.** `/v1/agent/screen-transaction` is provider-free, verifies a Skyfire payment token, constrains amount/currency to signed authorization, uses trusted server-side mapping and `RiskScreeningPipeline`, and marks `paypal_dispatch=DISABLED_NOT_CALLED`. `main_public.py` is fail-closed and does not initialize a provider. References: `app.py:209-220,280-314,316-327,336-416`; `tests/test_skyfire_api.py:601-614`; `main_public.py:1-16`. Test evidence: monkeypatched dispatch/provider functions fail if invoked and the test asserts disabled status; entrypoint test checks absence of provider setup/call (`tests/test_trustguard.py:526-530`). Tests were not executable in base environment. This is source separation, not service interoperability.

**PASS — LOCAL TEST ONLY credentials are separated from official verifier use.** The demo labels locally generated credentials and gates synthetic service identities; an official-verifier test rejects generated local credentials with fake JWKS, and absent Skyfire configuration leaves API screening unavailable. References: `scripts/run_paypal_sandbox_demo.py:1-7,34-48`; `tests/test_sandbox_demo.py:65-83,479-506`; `tests/test_skyfire_api.py:629-639`. Test evidence is source/mock coverage; pytest unavailable. **Operator prerequisite:** do not treat local generated credentials as production Skyfire authorization.

**PASS — No V4 candidate-selection status/threshold was found wired into reviewed payment authorization paths.** The reviewed transaction paths use configured/default `SyntheticIsolationForestScorer` and persisted assessment; the public route is provider-free. This is bounded to reviewed paths, not a claim of production calibration. References: `trustguard.py:670-715,772-823`; `app.py:184-187,383-389`; tests: `tests/test_trustguard.py:555-612`.
